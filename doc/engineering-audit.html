改进同卷操作的跨进程互斥

本机按卷标识建立命名管道锁，独立工具包与 Pi 进程共享；卷标识统一大小写和尾部斜线，不包含工具包目录、会话 ID 或盘符。占用时拒绝操作，取得锁后由 Windows 接口重新核对身份、盘符与状态。

锁覆盖本次交互、提交与复查，进程退出由操作系统释放。Windows 后台解密仍通过 status 查询，不持锁等待整个转换过程。

E4

失败输入怎样恢复，才能避免重复执行？

恢复语义 · 已用隔离脚本复现阻塞

“收件箱”是 Web 后端保存已接受输入的持久化投递队列：消息先落盘，再交给 Pi；它记录 pending（等待）、delivering（投递中）、delivered（已投递）和 failed（失败），负责排队、去重和重启核对。

收件箱出现 failed 条目后停止投递。新消息可以接受并落盘，但仍停在 pending；编辑和删除只接受 pending 条目。因此用户无法通过现有队列接口解除失败项阻塞。

first → failed→提交 second→second → pending
模型调用仍只有 first

“失败后停住”和“不自动重放”符合现有规格。需要补充用户主动恢复动作。强杀留下的 delivering 状态可能已发送给模型，恢复时还需要区分结果未确认。

状态直接重试的风险可选动作
failed失败发生在模型接受前后，含义可能不同显式跳过，或以新 ID 重新提交
重启后的 delivering模型或工具可能已执行先查历史与工具结果，明确确认后再决定
建议：提供“跳过此项”和“重新提交”两种显式动作。对结果未确认项优先核对状态，禁止自动重放；选择跳过也应持久化记录。
代码、规格与复现结果
  • SessionInbox：drain() 在任何 failed 时返回；change() 仅选择 pending。
  • 输入收件箱规格：投递失败停住、不重放。
  • 隔离复现：第一次 prompt 抛错，再接受第二条；结果 calls=[first]，队列状态 [failed,pending]。没有真实模型请求。
  • 现有收件箱测试保留失败不自动重放，但未定义主动解除步骤。
