# 实测记录

状态：四轮实测已归档。只保留会影响后续决策的数字，原始记录在临时目录，不随仓库保留。更新：2026-09-21。

环境：Windows 10/11 x64，Node 22.23.2，Bun 1.4.2，Chromium 86.0.4240.0（trunk 快照 r800229），Chrome 153.0.8010.48，全部经本机回环，无真实网络延迟。

## 1. 文件数决定解压时间

同字节数两组，同一卷，各跑两次取较快一次。

| 形态 | 文件数 | 体积 | 解压 |
|---|---|---|---|
| 多文件 | 1,276 | 24.9 MB | 506 ms |
| 少文件 | 2 | 24.9 MB | 33 ms |

本次两组耗时相差约 15 倍，按文件数差估算约 0.37 ms/文件。该结果仅说明本次同体积样本的文件数量影响，不用于推断压缩率与耗时的一般关系。

这是本目录里唯一一条把「文件数」换算成「用户等待」的依据。

## 4. 页面形态对比：A1b 与 A2

同一套外壳、同样 5 个页面，两个应用。A1b 是 Vite + react-router 框架模式 SPA；A2 是 Next 16.3.5 `output: 'standalone'`。冷缓存，每项 3 次取中位数。

### 首屏

| 页面 | 指标 | A1b | A2 | 差 |
|---|---|---|---|---|
| `/` | 外壳可见 | 18.0 ms | — | |
| `/` | **真实内容可见** | **70.0 ms** | **15.3 ms** | +54.7 ms |
| `/dashboard` | 外壳可见 | 14.1 ms | — | |
| `/dashboard` | 真实内容可见 | **27.4 ms** | **19.3 ms** | +8.1 ms |
| `/s/demo-1` | 外壳可见 | 19.4 ms | — | |
| `/s/demo-1` | 真实内容可见 | **36.5 ms** | **20.9 ms** | +15.6 ms |
| 三个页面 | **FCP** | **40 / 28 / 32 ms** | **40 / 28 / 32 ms** | **0** |

A1b 的静态 HTML 里有外壳和占位文字，所以 FCP 与 A2 相同，不白屏。差别只在「看到真实内容」这一步。A2 的服务端 HTML 里直接有内容。

### 路由切换

| 切换 | A1b | A2 |
|---|---|---|
| `/` → `/dashboard` | 21.0 ms | 18.1 ms |
| `/dashboard` → `/s/demo-1` | 21.7 ms | 34.1 ms |
| `/s/demo-1` → `/settings` | 27.4 ms | 22.4 ms |

**三个数两两之间都在同一次运行的抖动范围内。** 本机回环上分不出高下。

### 体积

| 项 | A1b | A2 |
|---|---|---|
| 页面产物 | 16 文件 / 357,973 B | 12 文件 / 590,088 B |
| 页面产物 gzip | 116,249 B（113.5 KiB） | 180,881 B（176.6 KiB） |
| 单次冷加载（实测传输） | 360,432 B，**未压缩** | ~154,130 B，**已压缩** |
| 单次冷加载，对齐压缩口径 | ~114,700 B（112.0 KiB） | 153,878 B |
| 服务端树 | 无 | 1,288 文件 / 26.8 MiB |

两类「传输字节」不能直接比：探测用的静态服务器不压缩，Next 的服务端压缩。对齐后 A1b 反而更小。

另有一条与体积无关但影响体验：静态服务器必须给产物配正确的缓存头。实测用的最小实现是 `no-store`，每次整页加载都重下 358 KB。

## 6. 框架与库在 Chromium 86 上的表现

| 对象 | 版本 | 结果 |
|---|---|---|
| React | 19.3.0 | **通过。** 与 18.3.1 逐项对照，渲染、事件、重渲染、`useEffect`、条件分支、样式全部一致，控制台零报错 |
| React | 18.3.1 | 通过 |
| react-router 框架模式 SPA | 8.4.0 | **通过。** 客户端跳转、`clientLoader`、`clientAction`、前进后退、深链接全部正常，零报错 |
| react-router 框架模式 SPA | 7.18.4 | 通过，与 8.4.0 逐字段一致 |
| Next.js 客户端运行时 | 16.3.5 默认配置 | **不通过。** 见第 7 节 |
| Vite | 8.3.0 | 产物在 86 上解析并执行正常。设与不设 `build.target: 'chrome86'` 行为相同 |

三份产物（react-router 8.4.0、7.18.4、不设构建目标）静态扫描后，都只命中 `??=` / `||=` / `&&=` 与 `??`，**没有命中任何 86 之后的内置方法或语法**。

`build.target: 'chrome86'` 设上不花代价（产物略小），建议保留作保险；当前依赖不设也能跑。

### react-router 8.4.0 SPA 模式的已知行为

首次直接打开一个不匹配任何路由的路径，控制台有一条 `React error #418`（hydration 失配）。**在 Chrome 153 上同样出现，同一处调用栈**，与内核无关。页面可用，客户端会重建这棵树。成因是构建期烘进 HTML 的 `HydrateFallback` 与客户端立刻渲染的错误边界对不上。

另两条构建约束：

| 约束 | 说明 |
|---|---|
| SPA 模式下 `HydrateFallback` 只能在 root 路由 | 子路由写会被构建期拒绝 |
| `clientLoader.hydrate = true` | 不写这一行，首屏 hydration 时不执行 loader，深链接拿不到数据 |

## 7. Next.js 的版本边界与配置

### 边界

按默认配置：**Next ≤ 16.1.7 在 Chromium 86 上正常，≥ 16.2.0 不执行。**

| Next 版本 | 产物里的 `static{}` | Chromium 86 客户端 |
|---|---|---|
| 13.5.11 / 14.2.35 / 15.5.25 | 0 | 通过 |
| 16.0.0 / 16.1.7 | 0 | 通过 |
| **16.2.0** | 1 | **失败** |
| 16.3.5 | 1 | 失败 |

根因：ES2022 静态初始化块 `static{}`（需要 Chrome 94+），86 的解析器直接抛 `SyntaxError`，整个 chunk 作废。首个带该语法的文件是 `dist/client/components/error-boundary.js`，16.2.0 起出现。

### 配置项

| 配置项 | 结果 |
|---|---|
| **`package.json` 里的 `browserslist: ["Chrome >= 86"]`** | **有效。** `static{}` 归零，86 上全部恢复 |
| `next.config` 的编译目标选项 | **不存在这个选项** |
| `transpilePackages: ["next"]` | 无效 |
| `.swcrc` | 完全被忽略（产物逐字节相同） |
| `next build --webpack` | **更差。** 7 处 `static{}`，产物是 Turbopack 的 1.6 倍大 |

### 修复的代价

| 项 | 默认 | `Chrome >= 86` | 差 |
|---|---|---|---|
| `.next/static` 文件数 | 12 | 12 | 0 |
| `.next/static` 体积 | 575,667 B | 576,569 B | +902 B |
| standalone 文件数 | 1,277 | 1,277 | 0 |
| 构建耗时 | 7.0–7.7 s | 7.1–7.2 s | 无差异 |

本样例文件数不变、体积增加 902 B，构建耗时差异在测试波动范围内。

### 默认编译目标的变化

| Next 版本 | 默认目标 |
|---|---|
| 13.4 – 15.5 | `chrome 64, edge 79, firefox 67, opera 51, safari 12` |
| **16.0.0 起** | `chrome 111, edge 111, firefox 111, safari 16.4` |

Next 官方声明的基线就是 Chrome 111+，与实测一致。拿一个要求 111 的框架去跑 86，瓶颈就在这里。

### 残留风险

降级只解决**语法**，不解决**运行时 API**。`Chrome >= 86` 的产物里仍有 86 缺失的 API 调用：

| API | 需要 | 情况 |
|---|---|---|
| `Object.hasOwn` | Chrome 93 | 特性检测 + 补丁写法，安全 |
| `reportError` | Chrome 95 | 有 `typeof` 判断，退回 `console.error`，安全 |
| `Array.prototype.at()` | Chrome 92 | 2 处，在重定向错误处理路径。**本次未触发，属于未验证项** |

### 降版本到 16.1.7 或更早的代价

| Next 版本 | 发行集文件数 | 构建耗时 | 构建器 |
|---|---|---|---|
| 13.5.11 | 1,782 | 18.1 s | webpack |
| 14.2.35 | 1,752 | 15.6 s | webpack |
| 15.5.25 | 1,958 | 24.5 s | webpack |
| 16.0.0 | 950（未含 static） | 7.8 s | Turbopack |
| 16.3.5 + `browserslist` | 1,289 | 7.1 s | Turbopack |

15 及以下会带入约 599 个 `caniuse-lite` 文件（运行时不用）。此外 14.x 及以下已不在官方支持列表；`next@16.0.0` 安装时 npm 报安全漏洞告警。

**结论：降版本比加一行 `browserslist` 更差。**

## 8. Tailwind 在 Chromium 86 上

| 形态 | 结果 |
|---|---|
| **Tailwind 3.4.18** | **受测项目通过。** 颜色、半透明、任意值、阴影、ring、渐变、动画、过渡、间距全部正确 |
| **Tailwind 4.3.3，原样** | **多数受测样式失效。** `bg-blue-500` 变透明、`text-red-600` 退化成黑色、阴影/ring/渐变/过渡全部没有。不白屏、不报错，只是样式没了。解析出的规则数 54 → 26 |
| Tailwind 4.3.3，展开 `@layer` 后 | 大部分恢复。颜色、半透明、任意值、阴影、渐变、过渡、动画回来了；**`space-*` 与 `ring-*` 仍然失效** |

三个成因，按影响排序：

| # | 原因 | 说明 |
|---|---|---|
| 1 | **`@layer`** | 86 把 `@layer` 块整块丢掉。v4 的产物是 `@layer theme` + `@layer base` + `@layer utilities`，于是主题变量和全部工具类一起消失 |
| 2 | **`:where()`** | `space-x-4` 编译成 `:where(.space-x-4 > :not(:last-child))`，86 丢弃该规则 |
| 3 | `var(--x,)` 空回退 | `ring-2` 的 `--tw-ring-shadow` 声明被丢弃，ring 画不出来 |

**实测确认下列两项在 86 上正常，容易被误认为原因：**

| 项 | 实测 |
|---|---|
| `@property` | 86 **支持**（Chrome 85 起），能注册、`initial-value` 生效 |
| `color-mix()` / `lab()` | 86 不支持，但 v4 的产物是两层写法（先给 hex，再在 `@supports` 里升级）。**回退生效**，前提是 `--color-*` 的定义没被 `@layer` 一起丢掉 |

展开 `@layer` 有两条路，都实测过：构建后处理产物 CSS；或把 `@import "tailwindcss"` 换成分别 import `theme.css` / `preflight.css` / `utilities.css`。**但两条路都修不掉 `space-*` 与 `ring-*`。**
