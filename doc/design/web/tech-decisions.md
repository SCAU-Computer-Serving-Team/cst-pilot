# Web 技术决策

状态：产品方向与技术栈已定，可进入架构设计；尚未实现。更新：2026-09-11。

需求见 [PRD](../../PRD.md)，安排见 [Todo](../../Todo.md) 第 3 条。

## 产品目标

自制 `@cst-pilot/web`，在本项目开放的能力范围内，完整替代 TUI 的操作界面。Web 与 TUI 共用 pi 内核、隔离 home 和当前会话，保留 TUI 通道。

| 范围 | 决策 |
|---|---|
| 使用者与场景 | 计维队员在机主电脑上诊断；浏览器与诊断后端运行在同一台电脑 |
| 交互功能 | 覆盖消息收发、流式输出、工具卡片、中断，以及本项目使用的会话管理、模型选择、凭据配置和扩展交互 |
| 完整替代的含义 | Web 打开后，本项目范围内的操作均可在 Web 完成 |
| 额度查询 | 只维护 `cstoa`（社团自建中转站）的额度，跟着它一并做；第三方 provider 不做查询，只给官方页面的跳转入口 |
| 开发阶段 | 分阶段实现完整目标；首个阶段的功能清单由架构拆分确定 |
| 能力边界 | 仅开放本项目允许的读取、检索与诊断能力 |
| 分发目标 | Web 随便携发行版提供，前端预构建，解压即用 |
| 系统范围 | Windows 10/11 x64；PE、裁剪系统和特殊介质单独验证 |

运行约束沿用 [README](../../../README.md)、[设计备忘](../../Notice.md)和[工具文档](../../tool/README.md)。诊断工具不修改系统配置；配置、会话和必要临时文件按现有隔离目录管理，这些限制不构成操作系统沙箱。

## 承载与启动

服务端采用 pi 扩展，首选与 pi 同进程运行。是否足以覆盖完整 Web 交互，需在架构阶段做最小验证。

| 事项 | 决策 |
|---|---|
| 包标识 | `@cst-pilot/web`，写入 Web 工程 `package.json` 的 `name` |
| Web 工程根目录 | `agent/home/extensions/web/`，集中存放前后端源码、共享类型、样式、资源和 Web 专用构建配置 |
| 服务端入口 | `agent/home/extensions/web/index.ts` |
| 源码组织 | 前端、服务端和共享模块在 Web 工程内分目录存放；内部目录名在架构阶段确定 |
| 前端产物 | `agent/home/extensions/web/static/`，不入 Git |
| 启动 | 通过 `pi.cmd` 启动 pi，再执行 `/web` 自动打开本机浏览器 |
| 版本选择 | `/web` 或 `/web n` 打开现代版；`/web o` 打开兼容版 |
| 会话关系 | 切换界面版本不新建 Agent 会话；TUI 与 Web 操作同一后端会话 |
| 端口 | 固定偏高端口，具体数值在架构阶段确定；占用或启动失败时明确报错 |
| 监听范围 | 仅本机回环地址，不提供局域网或远程访问 |
| 运行依赖 | 使用仓库或发行包自带运行时；现场无需安装 Node、npm 或执行构建命令 |
| 页面资源 | 脚本、样式、字体等必要资源随包提供；页面加载不依赖 CDN，模型和联网工具仍按各自配置访问网络 |

按首选同进程方案，pi 进程退出时 Web 服务随之停止。浏览器关闭与 Agent 任务的关系在架构阶段明确。

### 包命名与目录边界

Web 相关实现统一放在扩展目录内。pi 支持带入口文件、辅助模块和独立依赖声明的扩展目录。

本项目自定义包统一采用 `@cst-pilot/<名称>` 标识，`@cst-pilot` 是包作用域。Web 包名为 `@cst-pilot/web`，目录名为 `web`。

| 边界 | 要求 |
|---|---|
| pi 加载 | `index.ts` 作为扩展入口，只引入服务端运行所需模块；浏览器组件和 Vite 等构建工具不进入扩展启动依赖链 |
| 开发配置 | Web 专用的 `package.json`、锁文件、构建脚本和 TypeScript 配置放在本目录内；双版本依赖组织后定 |
| 共享模块 | 前后端共享类型和数据转换代码，不将 Node API、凭据读取或诊断执行代码带入浏览器产物 |
| 静态服务 | 只向浏览器提供 `static/` 中的构建产物，不将整个扩展工程目录作为静态资源目录 |
| 项目接入 | 现有启动器、检查入口和 `pack` 脚本负责调用 Web 工程；Web 实现与专用构建逻辑留在扩展目录内 |
| 运行数据 | 会话与凭据保存在隔离 home，临时状态按项目约定放置 |

## 前端技术栈

采用 TypeScript、React 和 Vite。一份业务逻辑与渲染源码配两套样式，分别构建现代版与兼容版。

| 事项 | 决策与约束 |
|---|---|
| 现代版 `modern` | React 19 + Tailwind CSS v4，承载主要视觉与动效设计 |
| 兼容版 `compat` | React 18 + Tailwind CSS 3.4 |
| 共享源码 | 共享代码与组件依赖需兼容两版 React，不能直接依赖 React 19 独有 API |
| 两套样式 | 共用业务含义和组件接口，分别处理两版 Tailwind 的样式差异 |
| 构建工具 | Vite；具体版本、依赖组织、锁文件及分发构建配置在实现时确定 |
| 组件来源 | 允许第三方库；Tim 选择参考组件，采用前检查双版本适配成本 |
| 页面组织 | 不引入前端路由库；设置等内容通过组件展开、折叠或弹出呈现 |
| 图表与动效 | 后续按设计选择现成库；兼容版允许简化效果 |

兼容性是选型和实现的方向约束，不作为本阶段的验收门槛。两版保持相同的业务操作和诊断含义，视觉效果可以不同。两档对应的最低内核、入口命令与支持清单见 [浏览器支持](browser-support.md)。

### 兼容性判断

Chromium 86 是兼容目标，尚未形成可用性保证。浏览器品牌、系统自带浏览器和静态扫描结果都不能代替实际内核验证；未验证前一律标为目标支持。

兼容版的写法约束见 [设计标准](design-standards.md) 兼容版降级，已做的实测见 [技术调研](tech-research.md)。

## 会话与交互

后端维护会话事实，两个界面反映同一份执行结果。Web 可维护输入草稿、展开状态、连接状态和展示缓存，不独立修改会话历史或执行状态。

| 事项 | 决策 |
|---|---|
| 消息输入 | TUI 与 Web 均可提交消息，已接受的输入与执行结果同步到两边 |
| 执行与中断 | 复用 pi 的执行、排队与取消语义 |
| 会话管理 | 覆盖本项目所需的新建、恢复、切换及其他会话操作 |
| 配置 | 模型与凭据使用后端现有配置体系 |
| 扩展交互 | 盘点当前扩展的命令、选择、确认和自定义界面，设计对应 Web 操作 |
| 传输 | 不采用 WebSocket；具体 HTTP 请求和事件传输方式在架构阶段确定 |
| 恢复 | 刷新、断线和会话切换后，从后端恢复当前会话与执行状态；恢复协议在架构阶段确定 |

接口与类型优先依据当前 pi 公开 API。接口组织可参考 Next App Router，具体目录在架构阶段确定。

## 诊断卡片

每个诊断工具设计对应卡片，展示每次调用的输入、执行状态与输出。卡片通过消费函数适配现有结构化结果。

| 情况 | 展示要求 |
|---|---|
| 成功 | 展示有效结果及解释数据口径所需的说明 |
| 执行中或中断 | 保留当前状态和已有结果，不能显示为已完成 |
| 整次失败 | 展示 `isError` 与失败原因；不能假定每次返回都是正常业务 JSON |
| 部分失败或权限不足 | 保留可用数据，同时展示 `notice`、`degraded`、采集错误等说明 |
| 缺失数据 | 根据错误和说明解释 `null`、空数组，不能一律呈现为正常或零值 |
| 输出截断 | 明确标注截断和统计范围，不把裁剪后的列表当作全部结果 |
| 暂无专用卡片 | 提供通用结果展示，避免读取、检索或其他已开放工具的结果丢失 |

现有工具的模型文本与 `details` 用途不同，且各工具的 JSON 包装结构并不统一。架构阶段需确定实时事件、历史记录与卡片数据的映射，以及大结果的传输和渲染方式。字段语义以[工具文档](../../tool/README.md)为准。

## 只读与访问边界

Web 沿用项目的只读工具策略，并提供必要的本机访问保护。仅监听回环地址不能代替请求校验，工具只读也不能消除诊断数据泄露和非预期模型调用的风险。

| 边界 | 要求 |
|---|---|
| 工具权限 | 服务端控制允许的工具集合；新建、恢复、切换会话和修改设置时，前端均不能扩大集合 |
| 扩展权限 | 不将 `defaultTools` 视为完整权限机制；扩展工具和命令也需纳入项目能力范围 |
| 项目隔离 | 保持隔离 home、`defaultProjectTrust=never`、上下文与技能加载限制，不加载机主目录中的陌生资源 |
| 请求来源 | 校验 `Host`、`Origin` 等来源信息，限制跨站访问；具体规则随接口设计确定 |
| 数据输出 | 只提供界面所需数据，不提供 home 目录或任意路径的直接下载接口，不返回完整配置对象 |
| 凭据 | 由后端保存与使用；Web 提供配置入口，已有密钥不随会话快照返回，也不持久化到浏览器存储 |
| 内容呈现 | 模型输出、工具文本和机主文件内容按不可信内容处理，不作为任意 HTML 或脚本执行 |

配置、会话与临时文件继续遵循现有目录约定。使用机主浏览器可能留下浏览器记录，不承诺零宿主痕迹。

## 开发与分发

开发仓库保留源码，发行包携带可直接运行的产物。具体打包方式在实现阶段确定。

| 事项 | 决策 |
|---|---|
| 设计流程 | 先用 Pencil 制作页面原型，再确定前后端契约；动效在设计阶段专门处理 |
| 开发方式 | 使用 AI 辅助实现，开发服务器和调试回路随架构确定 |
| 依赖 | 允许第三方库；控制分发文件数量，避免将开发依赖树直接带入发行包 |
| 双版本产物 | 两版均随包提供，命令选择所打开的界面版本 |
| 打包接入 | 后续接入现有 `pack` 流程，为 Web 明确运行文件清单；保留扩展入口、服务端运行文件与必要依赖、两版静态产物及许可证，排除前端源码、开发依赖和构建缓存 |
| 包形态 | 本仓库内的 pi 扩展，随便携发行包交付 |
| 检查与验证 | 引入第三方兼容检查工具；具体测试范围、脚本和自动化方式在开发时确定 |

当前 `pack/pack.mjs` 会整目录复制 `agent/home/extensions/`。Web 工程加入后必须调整这条规则，避免开发文件随包分发；具体构建、文件复制、完整性检查和凭据排除方式在打包接入时落实。

### 技术依据

以下依据来自本地 pi 0.85.1 的文档、类型与源码。完整 Web 交互仍需运行验证。

| 依据 | 结论与限制 |
|---|---|
| 扩展发现与依赖规则 | 支持 `extensions/*/index.ts` 及扩展目录内的 `package.json`；前端源码可同目录存放，但不得被服务端入口作为运行依赖加载 |
| `pi.sendUserMessage()`、消息与工具事件、`ctx.abort()` | 支持注入用户消息、订阅执行过程和中断；双端一致性仍需应用层设计 |
| `ExtensionCommandContext` | 新建与切换等会话控制接口有上下文限制；不能假定任意 HTTP 回调都能安全调用 |
| `session_shutdown` / `session_start` | 会话切换会销毁并重新加载扩展；服务端生命周期必须随之处理 |
| 长驻资源约定 | 在会话开始或需要资源的命令中启动，在关闭事件中释放；不能在扩展工厂加载时无条件监听端口 |
| 二进制构建脚本 | `build:binary` 用 `bun build --compile` 产出单文件二进制；扩展在所有运行模式下都由 jiti 加载（`dist/core/extensions/loader.js`）。二进制模式下 jiti 走 `virtualModules` 白名单（pi 全家桶与 typebox）且 `tryNative: false`，原生模块不可用；扩展自身的 `node_modules` 纯 JS 依赖可从磁盘解析 |

本地依据位于 `agent/node_modules/@earendil-works/pi-coding-agent/` 下的 `docs/extensions.md`、`dist/core/extensions/types.d.ts`、`dist/core/agent-session.js` 和 `package.json`。升级 pi 后需重新核对相关接口与运行行为。
