# 阶段 8.5：阶段 9 前置架构清理与包边界收口设计

阶段 8.5 位于阶段 8（Web 端适配）与阶段 9（GPUI 桌面端）之间，保持对外 HTTP/SSE 协议与旧版 `v0.6.2` 兼容性不变。本阶段抽离跨进程基础库 `cst-os` 与独立更新器 `cst-updater`，为 `pi-runtime` 增加可选编译开关（Cargo Feature），同时收口同一工具包目录的升级写入锁、统一服务端写接口加锁顺序并完成字体构建解耦，为阶段 9 引入 `cst-client` 与 `cst-desktop` 做好依赖与接口准备。

总体路线见 [0.PLAN.md](0.PLAN.md)，前置设计见 [6.cst-pilot.md](6.cst-pilot.md)、[7.server.md](7.server.md) 与 [8.web.md](8.web.md)，后续衔接见 [9.desktop.md](9.desktop.md)，架构取舍见 [ADR.md](../../ADR.md)。

## 批次 3：拆包更名、共享契约与唯一升级写入锁

确立 `cst-kit -> cst-updater -> cst-os` 单向依赖链，严格克制 `cst-os` 体积，确保跨进程锁兼容既有协议，并保证同一工具包目录共用唯一 `ActivityGate`（升级写入锁）。

### 3.1 依赖方向与三包归属

`update/verify.rs` 当前混杂异步下载与本地目录树校验，`manifest.rs` 调用 `network::release_url`，`handoff.rs` 与 `applier.rs` 交叉依赖暂存目录与执行逻辑。为避免反向依赖，并让宿主侧（`cst-kit`）与独立更新器（`cst-updater.exe`）共用同一套验签和目录树校验规则，确立单向链路：**`cst-kit -> cst-updater -> cst-os`**。

| 包名 | 产物 | 职责归属 | 真实依赖边界 |
|---|---|---|---|
| `crates/cst-os` | 库 | 仅收**真实跨进程共享原语**：<br>1. 工具包路径定位与根解析（`KitLayout`、`resolve_kit_root`）<br>2. `.state/server.json` 读写契约与 `ProcessIdentity`（供 `cst-server`、`cst-updater` 与阶段 9 `cst-client` 共用，客户端不反向依赖 `cst-server`）<br>3. Windows UAC 管理员令牌校验<br>4. 安全目录锚定、重解析点校验与带退避的原子写（`Storage`、`atomic_write_*`、`is_storage_full_io`）<br>5. 统一跨进程锁原语（严格保留既有锁名、键规范化与冲突语义）<br>6. 升级交接（宿主写入更新请求并拉起 `cst-updater.exe`）与事务协议数据结构，以及有界严格 JSON 解析 | 零 `pi-*`、零 `wmi`、零 `reqwest`、零 `rquickjs`；仅含 `serde`、`serde_json`、`sha2`、`same-file` 及 `windows` 最小子集 |
| `crates/cst-updater` | 本地校验与替换库 + CLI 入口 `cst-updater.exe` | 离线签名校验（`ReleaseKey`、清单与 `SHA256SUMS` 双重 Ed25519 验签）、本地 ZIP 与目录树全量哈希校验及凭据扫描、发行目录白名单分类（`layout.rs`）、预写事务读写、备份替换与逆序回滚（`applier`、`io`、`process`）、CLI 入口（`--root` / `--request` / `--recover`） | 仅依赖 `cst-os`、`ed25519-dalek`、`base64`、`zip`、`semver`、`uuid`、`regex`、`tokio-util`（取消令牌）与 `windows` 进程/空间子集；**零 `pi-*`、零 `reqwest`、零 `wmi`**。宿主侧与独立更新器共用编译期公钥配置（`CST_UPDATE_PUBLIC_KEY`） |
| `crates/cst-kit`（原 `cst-pilot`） | 库 | 17 个诊断与交付工具，诊断专用 Job Object 与 COM 包装，`PathGuard` 业务策略，BitLocker、Runbook、CSTOA 认证（含 `Clock`）与遥测，升级在线发现/下载/暂存编排（`network`、`service`、`activity`、`handoff` 宿主侧）及 `KitHost` | 依赖 `pi-{ai,agent,session,runtime}`（`pi-runtime` 设 `default-features = false`）、`cst-updater`、`cst-os` |

**明确留在各自所有者的非共享代码（不迁入 `cst-os`）**：诊断专用 Job Object 采集包装与 COM 初始化、`auth::oa::Clock`、`tools::PathGuard` 业务拦截规则、升级发行白名单（归 `cst-updater`）。

### 3.2 跨进程锁兼容要求

1. 统一锁封装必须**严格保留所有既有锁名、键规范化规则与冲突错误语义**，不得破坏 Rust [discovery.rs](../../../crates/cst-server/src/discovery.rs) 与旧 TS [owner.ts](../../../agent/home/extensions/runtime/owner.ts) 共用的跨进程会话锁。
2. 非 Windows 平台统一复用现成的操作系统文件锁（`fs2` / `File::try_lock_exclusive`，进程退出由内核自动释放），禁止改用易留崩溃残留的目录锁。

### 3.3 同一工具包目录的唯一升级写入锁与去全局单例规则

当前 `kit.rs` 与 `update/service.rs` 依赖 `ActivityGate::for_root` 全局静态表获取同一个升级写入锁实例。直接删除全局表若造成各自新建实例，会导致更新器误判空闲而业务仍在写入。

1. **显式注入唯一 `ActivityGate`**：在 `KitHost` / `Kit` 组合入口为同一规范化 `kit_root` 构造唯一 `Arc<ActivityGate>`，并显式注入 `Kit`、`UpdateService` 与 `ServerState`。单会话入口 `Kit::create_session*` 复用 `open_session_inner` 内核。
2. **单进程按目录共享运行期约束**：在组合层明确同一规范化 `kit_root` 在单进程内只共享同一活跃运行期，移除 `TelemetryService`、`UpdateService`、`ActivityGate` 的隐式静默覆盖行为（不再二次 `load` 时静默忽略新参数）。
3. **写锁替代先行**：移除 `runbook` / `auth` / `telemetry` 进程全局 `Mutex<()>` 前，先以绑定在 `Kit` / `KitHost` 实例上的按目录互斥锁配合内核命名管道锁承接并发写保护。
4. **必须补齐的回归测试**：验证同一工具包目录重复创建时共享唯一 `ActivityGate`，验证不同工具包目录相互隔离，并验证发起升级交接关闭 `ActivityGate` 后阻塞全部业务写入。同步将 `tests/update_applier.rs`（含 `CARGO_BIN_EXE_cst-updater`）迁入 `crates/cst-updater/tests/`，单独构建运行更新器并用阶段 8 事务样本验证 `--recover`。

### 3.4 同步收口全仓更名与文档归属

批次 3 同步完成以下更名引用切换，使阶段 9 直接基于阶段 8.5 结果施工：

- [9.desktop.md](9.desktop.md)、[0.PLAN.md](0.PLAN.md)、[doc/README.md](../../README.md)、[doc/TESTING.md](../../TESTING.md)、[doc/ARCHITECTURE.md](../../ARCHITECTURE.md) 与 `crates/cst-kit/lhm-host/publish.ps1` 中全部 `crates/cst-pilot` 路径与更名计划表述。
- [kit.rs](../../../crates/cst-kit/src/kit.rs) 清理：`CstPilotExtension` 仅构造一次、`CompositeDataPolicy { gate, privacy }` 显式组合（切断 `update -> bitlocker` 委托）、`diagnostics::definitions` 移除先构建 5 个工具再 `retain` 过滤掉 2 个的冗余逻辑、`OPEN_TOOL_NAMES` 增加一致性断言、`check_resources` 不再构造全部工具。

## 批次 4：`cst-server` 写接口加锁顺序、错误映射与协议回归

建立全服务唯一的写接口加锁顺序并把慢等待移出锁外，保持 100% HTTP/SSE 协议与错误码兼容，同时清理前端明确缺陷。

### 4.1 统一写接口加锁顺序与持锁范围

所有写操作必须遵守固定获取次序，禁止反向加锁：

```text
1. 路径与请求体无锁校验
2. KeyedLocks（作用域锁：session:{id} / auth:{pid} / auth-config:all / model-selection:{id}）
3. ModeController::admit_write（通道准入读锁）
4. ActivityGate 租约获取（升级互斥）
5. MutationReceipts 写入 started 回执 -> 立即 drop(ModeController 读锁)，保留 ActivityLease 至动作结束
```

- **剥离锁内慢操作**：`routes/auth.rs` 中等待 OAuth 任务取消/结束与外部网络请求移至释放 `ModeController` 读锁之后执行，避免阻塞 `close_web()` 写锁。
- **保留特殊准入端点**：通道切换端点（`/api/app/web/open`、`/api/app/web/close`）与阶段 9 新增更新控制端点（`/api/app/update/*`）按各自独立门禁规则处理，不套用普通会话写接口锁链。

### 4.2 协议兼容与强类型校验约束

1. **保留缺省与显式 `null` 的区分**：例如 `POST /api/sessions`（`routes/sessions.rs:191-238`）允许字段缺省但拒绝显式 `null`。引入强类型请求 DTO 时，对这类字段采用能区分未传与显式 `null` 的反序列化类型。用 `api_contract` 测试证明状态码与错误码、文案及 SSE 事件形状保持一致。
2. **错误模型与 ID 校验**：将内部错误收敛到 `ServiceError`、`ModeRejection`、`StorageError`（消除字符串前缀匹配）。ID 校验仅共用基础安全字符检查函数，保留 `session_id`、`request_key`、`provider_id`、`client_id` 各自的长度与格式约束。
3. **模块边界收口**：
   - 拆出 `routes/exports.rs`、`routes/events.rs`、`routes/settings.rs` 与 `SessionIndexStore`。`exports/store.rs` 复用 `cst_os::fs_safe` 并将同步文件 I/O 移入 `spawn_blocking`。用 `slot.display_title()` 替代导出路由中全盘 `pool.list()` 扫描。
   - `AuthRuntime` 暴露统一方法清零 `cst-server` 内 6 处 `"cstoa"` 特判。`/api/state` 命令列表从 `cst_kit::SKILL_NAMES` 动态生成。`runbook` 解析与 BitLocker 验证结果合成迁回 `cst-kit`。`SlotInboxExecutor::was_accepted` 脱离 `MessageDecorators`。

### 4.3 前端低风险缺陷与死代码清理

1. 修复 `src/web/frontend/app/routes/tree.tsx` 遗漏 `useEffect` 依赖数组导致重复绑解 `keydown` 的问题。
2. 修正 `shell/shell.tsx` 错误的 GitHub 组织链接、预览模式硬编码个人标识，以及对用户暴露「pi / models.json」的提示文案。
3. 删除 `tool-card.tsx` 中的 `SearchRow` 与 `map-tool.ts` 中 `runbook` / `sys overview` 不可达分支，合并 `CollapsedToolGroup` 与 `ToolCard` 对 `mapTool` 的重复调用。
